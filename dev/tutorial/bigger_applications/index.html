﻿# Bigger Applications — Multiple Files

As your application grows you will spread logic across many files. Nitro uses the same Handlers / Routes separation that Django popularised: view-logic lives in handler modules, URL declarations live in a single routes file.

Start from Nitro.newapp

Nitro.newapp writes the layout below and the boot that runs it, the way Django's startproject does. It is public but not exported, so call it qualified:

julia> using Nitro, PormG

julia> Nitro.newapp("MyApp"; path = "myapp")

With PormG loaded it runs PormG's interactive PormG.setup to write db/connection.yml, then adds the database driver for the adapter you chose: SQLite for SQLite, LibPQ for PostgreSQL. Pass pormg = false for an app with an in-memory worker store and no database. path must not exist yet, or must be an empty directory.

$ cd myapp
$ julia --project -e 'using Pkg; Pkg.instantiate()'
$ export API_SECRET_KEY=$(openssl rand -hex 32)   # at least 32 bytes
$ julia --project -e 'using MyApp; MyApp.main()'

Recommended project layout

myapp/
├── Project.toml            # Nitro and PormG by URL, plus HTTP and the database driver
├── Manifest.toml           # written by the first Pkg.instantiate()
├── .gitignore              # excludes db/connection.yml: it holds the database password
├── db/
│   ├── connection.yml      # written by PormG.setup
│   └── models.jl           # your PormG models
├── src/
│   ├── MyApp.jl            # the module and its main() boot
│   ├── Routes.jl           # all path() declarations
│   └── Handlers/
│       └── HealthHandlers.jl
└── test/
    └── runtests.jl         # one internalrequest test

The src/ tree is a Julia package. Its module body only defines code: the using lines, the App and the includes. Everything that connects or starts runs in main(), shown in full under The boot newapp writes below. As the app grows, add a handler module per domain (ProductHandlers.jl, OrderHandlers.jl) and declare its routes in Routes.jl.

Setting up PormG models

PormG models live in db/models.jl, outside src/. Import them in the module body with @import_models, which creates a plain Julia module you can alias and pass down to handlers via import. Importing models only defines code, so it belongs in the module body.

Connecting does not. PormG.Configuration.load_many opens the database connection. A package's module body runs once, when it is precompiled, and loading the cached package does not run it again, so a connection opened there does not exist at runtime. Keep load_many in main(), where newapp puts it.

# src/MyApp.jl
module MyApp

using Nitro, PormG, SQLite

const app = App(mod = @__MODULE__)

# Import the model file — creates a module named `models`
PormG.@import_models "../db/models.jl" models

# Alias for convenience: handlers do `import ..appM`
const appM = models

include("Handlers/ProductHandlers.jl")
include("Handlers/OrderHandlers.jl")
include("Routes.jl")

# main() as `newapp` wrote it: `load_many` connects here, at runtime.

end # module

Handlers import the alias and use appM.Product.objects for queries:

# src/Handlers/ProductHandlers.jl
module ProductHandlers

using HTTP
using Nitro
using PormG
import ..appM   # the alias defined in MyApp.jl

export list_products, get_product

function list_products(req::HTTP.Request)
    query = appM.Product.objects
    return Res.json(list(query))
end

function get_product(req::HTTP.Request, id::Int)
    query = appM.Product.objects
    query.filter("id" => id)
    result = list(query)
    isempty(result) && return Res.json(Dict("error" => "not found"); status=404)
    return Res.json(first(result))
end

end # module

Defining handlers

Handler functions live in plain Julia modules — one file per domain area.

# src/Handlers/MathHandlers.jl
module MathHandlers

using HTTP
using Nitro

export multiply, divide

function multiply(req::HTTP.Request, a::Float64, b::Float64)
    return Res.json(a * b)
end

function divide(req::HTTP.Request, a::Float64, b::Float64)
    a == 0 && return Res.json(Dict("error" => "divisor cannot be zero"); status=400)
    return Res.json(a / b)
end

end # module

Declaring routes

All path() calls are collected in Routes.jl. This is the only place that wires handler functions to URL patterns.

# src/Routes.jl
module Routes

using Nitro: path, RouteDefinition
import ..MathHandlers
import ..ProductHandlers

urlpatterns() = RouteDefinition[
    path("/api/math/multiply/<float:a>/<float:b>", MathHandlers.multiply, method="GET"),
    path("/api/math/divide/<float:a>/<float:b>",   MathHandlers.divide,   method="GET"),

    path("/api/products",               ProductHandlers.list_products,  method="GET"),
    path("/api/products/<int:id>",      ProductHandlers.get_product,    method="GET"),
    path("/api/products",               ProductHandlers.create_product, method="POST"),
]

end # module

urlpatterns is a function, so the list is built when main() registers it. The module takes only path and RouteDefinition from Nitro: under a blanket using Nitro, defining its own urlpatterns would silently shadow Nitro's.

Splitting routes across files with include_routes

For larger apps, split urlpatterns into per-domain files and compose them with include_routes.

src/
└── Routes/
    ├── math_routes.jl
    └── product_routes.jl
# src/Routes/math_routes.jl  (included into `Routes`)
import ..MathHandlers

const math_routes = [
    path("/multiply/<float:a>/<float:b>", MathHandlers.multiply, method="GET"),
    path("/divide/<float:a>/<float:b>",   MathHandlers.divide,   method="GET"),
]
# src/Routes.jl
module Routes

using Nitro: path, include_routes, RouteDefinition
include("Routes/math_routes.jl")
include("Routes/product_routes.jl")

urlpatterns() = vcat(
    include_routes("/api/math",     math_routes),
    include_routes("/api/products", product_routes),
)

end # module

The prefix passed to include_routes is prepended to every path in the included list, so /multiply/<float:a>/<float:b> becomes /api/math/multiply/<float:a>/<float:b>.

include_routes returns a Vector{RouteDefinition}, not a single route, so compose several groups with vcat — nesting them in a plain [...] would build a vector of vectors, which urlpatterns() does not accept.

The boot newapp writes

This is src/MyApp.jl exactly as Nitro.newapp("MyApp") writes it when you choose SQLite. A test generates the app and compares the file with this page, so the two cannot drift apart.

<!– newapp:src/MyApp.jl –>

module MyApp

using Nitro, PormG, SQLite

const app = App(mod = @__MODULE__)

# Once db/models.jl defines models, import them here for the handlers (`import ..appM`):
#   PormG.@import_models "../db/models.jl" models
#   const appM = models

include("Handlers/HealthHandlers.jl")
include("Routes.jl")

"""
    main(; kwargs...)

Boot the app and serve it. Reads `PORT` (default 8000) and `API_SECRET_KEY` (at least
32 bytes); keyword arguments go to `serve` (tests pass `async = true`).
"""
function main(; kwargs...)
    sync_pormg_env!()  # NITRO_ENV -> PORMG_ENV, only when NITRO_ENV is set
    # PormG parses db/connection.yml, validates it and connects, from any working directory
    PormG.Configuration.load_many(["db"]; root = pkgdir(@__MODULE__))
    workers = worker_startup(app; queues = ["reports"], store = pormg_nitro_worker(db_key = "db"))
    urlpatterns(app, "", Routes.urlpatterns())
    serve(app; port = parse(Int, get(ENV, "PORT", "8000")), middleware = [workers],
          secret_key = SecretString(ENV["API_SECRET_KEY"]), kwargs...)
end

end # module

<!– /newapp –>

Line by line:

  • using Nitro, PormG, SQLite: SQLite is the driver for the adapter in db/connection.yml. A PostgreSQL app loads LibPQ instead.
  • const app = App(mod = @__MODULE__): the application handle that every routing and serving call takes. mod = @__MODULE__ is what serve(revise = …) tracks.
  • sync_pormg_env!() copies NITRO_ENV, when it is set, to PORMG_ENV, so PormG reads the same environment from connection.yml. Without NITRO_ENV, PormG uses default_env:.
  • load_many(["db"]; root = pkgdir(@__MODULE__)): PormG parses db/connection.yml, validates it and connects. root finds db/ next to the package rather than in the working directory, and the connection key stays "db".
  • worker_startup(app; …, store = pormg_nitro_worker(db_key = "db")): background tasks are stored in the database, on the same connection. See Workers.
  • urlpatterns(app, "", Routes.urlpatterns()) registers the routes. The prefix comes first, and "" is the root.
  • serve(app; …) is keyword-only. PORT defaults to 8000, and API_SECRET_KEY must hold at least 32 bytes. Keyword arguments to main go through to serve, which is how a test starts the server with async = true.

Global middleware goes in serve's middleware list, next to workers, and runs before every route, whichever handler it targets:

serve(app; port = parse(Int, get(ENV, "PORT", "8000")),
      middleware = [workers, SessionMiddleware(store = MemoryStore()), RateLimiter()],
      secret_key = SecretString(ENV["API_SECRET_KEY"]))

Middleware layers

Nitro supports middleware at three levels: global (via serve()), group (via the middleware= keyword on include_routes()), and route-level (via the middleware= keyword on path()).

Execution order is always:

global middleware → group middleware (outer group first) → route middleware → handler

Each list runs top-down, in the order written. The route is chosen between the global list and the rest. A middleware that rewrites the method or the path (X-HTTP-Method-Override, a legacy alias) therefore belongs in the global list, where the rewritten request still gets its new route's guards. See Rewriting the method or the target.

Global middleware

serve(middleware=[SessionMiddleware(store=MemoryStore()), RateLimiter()])

Route-level middleware

Apply middleware to individual routes by passing a middleware= vector to path().

const routes = [
    # public — no extra middleware
    path("/api/products", ProductHandlers.list_products, method="GET"),

    # protected — requires authentication. Guards reach a route through `GuardMiddleware`;
    # they are not middleware themselves.
    path("/api/products", ProductHandlers.create_product,
         method="POST", middleware=[GuardMiddleware(login_required())]),

    path("/api/products/<int:id>", ProductHandlers.delete_product,
         method="DELETE",
         middleware=[GuardMiddleware(login_required(), role_required("admin"))]),
]

Group middleware

include_routes can give a whole group of routes the same middleware (#439). It runs on every route in the group, ahead of each route's own list. The common use is an app that serves a browser UI and a bearer-token API: sessions and CSRF belong on the browser routes only.

browser = include_routes("", [
    path("/login", AuthHandlers.login_form, method="GET"),
    path("/login", AuthHandlers.login, method="POST"),
    path("/account", AccountHandlers.show, method="GET",
         middleware=[GuardMiddleware(login_required())]),
]; middleware=[SessionMiddleware(store=store), CSRFMiddleware(csrf_secret)])

api = include_routes("/api", [
    path("/products", ProductHandlers.list_products, method="GET"),
    path("/products", ProductHandlers.create_product, method="POST"),
]; middleware=[BearerAuth(validator)])

urlpatterns("", vcat(browser, api))

A POST /login meets SessionMiddleware, then CSRFMiddleware, then its handler. GET /account meets the same two, then its own GuardMiddleware. A POST /api/products never meets the session or the CSRF check.

Groups nest. An include_routes around another puts its own list first:

admin = include_routes("/admin", admin_routes; middleware=[GuardMiddleware(role_required("admin"))])
api   = include_routes("/api", vcat(public_routes, admin); middleware=[BearerAuth(validator)])
# GET /api/admin/users: BearerAuth → the admin guard → the route's own list → handler

Every route in a group shares the same middleware instances. One SessionMiddleware keeps one store, and its prune janitor starts once when serve() starts. Do not list the same layer at two levels, such as globally and in a group: the lifecycle is registered once, but the layer itself runs once per list it appears in, on every request.

Group middleware runs only on a request that matched one of the group's routes. A request that matches nothing (404), or matches a path but not its method (405), never reaches it. Keep layers that must see every request, such as rate limiting, access logging or ExtractIP, in the global list.

Per-route middleware and global middleware

Global middleware — the middleware=[...] you pass to serve — runs on every request, including requests that match no route (404) and requests whose path matches but whose method does not (405). A route cannot opt out of it.

Passing middleware=[] on a path() call means "this route adds no middleware of its own". It does not bypass the global chain:

# Global middleware still runs here — `middleware=[]` only means "no *extra* middleware",
# which is the same as omitting the kwarg. Prefer omitting it.
path("/health", HealthHandlers.ping, method="GET")

If a health-check endpoint must respond even when a dependency the global middleware needs is unavailable, make that middleware tolerate the failure — for example by skipping its work for specific paths — rather than expecting the route to escape it.

Internal requests

Use internalrequest to call one of your own endpoints from within another handler — for example, to reuse validation logic or chain computations:

using HTTP

function process_and_fetch(req::HTTP.Request, id::Int)
    # call another endpoint inside the same server
    inner = internalrequest(HTTP.Request("GET", "/api/products/$id"))
    data  = JSON3.read(inner.body)
    # ... further processing
    return Res.json(data)
end
An internal request skips your global middleware

internalrequest runs only the middleware you pass to that call, not the global list given to serve(middleware = …). Authentication, sessions, CSRF and rate limiting installed globally do not apply to it. Route and router middleware still run. Unless the request already carries a client IP, it is 127.0.0.1.

Build the target yourself, as above, from values you have already validated (id is an Int here). A handler that passes a client-supplied path to internalrequest lets that client reach every route guarded only by global middleware, as loopback.
