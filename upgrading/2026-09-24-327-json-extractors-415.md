## `Json{T}` / `JsonFragment{T}` / `MultipartForm{T}` — a body with the wrong `Content-Type` is a `415`

- **Version**: Unreleased
- **Nitro ref**: [#327](https://github.com/PingoLee/Nitro.jl/issues/327) ; `src/extractors.jl`,
  `src/errors.jl`, `src/utilities/misc.jl`, `src/utilities/bodyparsers.jl`
- **Recorded**: 2026-09-24
- **Severity**: breaking — a request to a `Json{T}` or `JsonFragment{T}` route that does not send
  a JSON `Content-Type`, including one that sends none, is answered `415` instead of being bound.

### What changed

| Extractor | Before | After |
|---|---|---|
| `Json{T}`, `JsonFragment{T}` | bound any body that parsed as JSON, whatever the `Content-Type` | require `application/json` or an `application/*+json` type (case-insensitive, parameters such as `charset` ignored); anything else, **including no `Content-Type`**, is `415 Unsupported Media Type` |
| `MultipartForm{T}` | a non-`multipart/form-data` request was a `400` | `415`; the type check is now case-insensitive too, though HTTP.jl's multipart parser still reads only the exact `multipart/form-data; boundary=…` spelling, so another spelling reaches the binder as an empty body (a `400`, as before) |

The 415 is a new exception, `UnsupportedMediaTypeError`, which `handle_error` answers with the fixed
body `{"message":"415: Unsupported Media Type"}` and which, like `ValidationError`, is logged at
`@debug` only.

Why: `text/plain`, `application/x-www-form-urlencoded` and `multipart/form-data` are the CORS
"simple" types, and so is sending no body type at all. A cross-site page can send any of them
without a preflight. An API that reads JSON regardless of the declared type accepts such a forged
request exactly as it accepts its own client's. SameSite cookies and `CSRFMiddleware` mitigate that,
but an app that uses `SameSite=None`, or that skips CSRF protection on the theory that "JSON APIs are
CSRF-safe", was exposed. Express's `json()` and Spring's `@RequestBody` refuse such bodies the same
way.

The bare parsers `json(req)` and `json(req, T)` are unchanged: calling one is an explicit decision to
read the body as JSON. `getjson` and `payload` change as well; see the separate entry for them.

### How to find the calls to migrate

```bash
# Routes whose clients must now send a JSON Content-Type.
rg -n 'Json\{|JsonFragment\{' <app>/src

# Tests (and scripts) that post JSON without a Content-Type -- the usual casualty.
rg -n 'Request\("(POST|PUT|PATCH|DELETE)",[^)]*\[\]' <app>/test
rg -n 'HTTP\.(post|put|patch)\(' <app>/test

# Code that expected a 400 from MultipartForm for a non-multipart request.
rg -n 'MultipartForm\{' <app>/src <app>/test
```

Browsers' `fetch` with a JSON body, axios, and HTTP.jl clients that pass the header all already
send `application/json`. The breakage is almost always hand-built requests in tests.

### Migrate your app

```julia
# ✗ before — bound, although the body never said it was JSON
HTTP.Request("POST", "/search", [], """{"q":"lamp"}""")

# ✓ after
HTTP.Request("POST", "/search", ["Content-Type" => "application/json"], """{"q":"lamp"}""")

# ✗ before — a test expecting a 400 from MultipartForm for a JSON body
@test internalrequest(app, json_req).status == 400
# ✓ after
@test internalrequest(app, json_req).status == 415
```
