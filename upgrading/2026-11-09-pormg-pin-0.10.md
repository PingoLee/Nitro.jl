## PormG moves to `0.10` — an app pinning `^0.9` must move too, and run PormG's own guide

- **Version**: Unreleased
- **Nitro ref**: #913 ; `Project.toml` `[sources]` + `[compat]`;
  the pins in `bench/juliac/pools`, `bench/juliac/realapp`, `bench/socket/db`
- **Recorded**: 2026-11-09
- **Severity**: **breaking (dependency resolution)** — an app carrying its own `PormG = "^0.9"`
  bound does not resolve against this release. Nitro's own API is unchanged.

### What changed

Both of Nitro's PormG pins moved together. **Only 0.10 is supported**: the bound is `^0.10`, not
`0.9, 0.10`.

| pin | before | after |
|---|---|---|
| `[sources]` `rev` | `2d461c3a086fdb2b04c8e97810578b777447fb9b` (PormG `main`, still version `0.9.0`) | `6e8364f7fcc4773993e9553155a5dea0d6d57865` (`v0.10.0`'s commit) |
| `[compat]` | `PormG = "^0.9"` | `PormG = "^0.10"` |

As before, the `rev` is the commit the tag points at, not the tag, which can move. The previous
`rev` already carried PormG's 0.10.0 changes; between the two commits only PormG's version and its
upgrade entries' `Version` lines moved. Nitro's adaptations to them shipped with #791: the
`Models.@models` line in the tutorial and in the models file the `newapp` test writes, and the
`register_connection(…; change_data)` keyword.

### Who this affects

Every app that uses `NitroPormGExt`, which is every app that reaches PormG directly. Nitro mediates
only its own two tables (`nitro_session`, `nitro_task`), and **does not insulate an app from
PormG's 0.10.0 changes**: run PormG's guide from `v"0.9.0"` against your own code. The entries most
likely to reach a Nitro app:

- **PormG #1602 + #1650 — a models module declares its models with `Models.@models`.** A models
  file `include`d in the module body and bound with `set_models` (the boot `Nitro.newapp` writes,
  and the one in `docs/src/tutorial/bigger_applications.md`) needs a `Models.@models Product …`
  line after its models, or `set_models` raises `ModelDefinitionError`. A file loaded with
  `@import_models` gets the line generated. PormG now writes typed bindings
  (`Product::Models.ModelType = …`); a plain or `const` file still loads.
- **PormG #1601 — every relation resolves to a model at `set_models`**, or registration refuses.
  A `ForeignKey("Name")` whose target no registered module declares now fails at boot, not at the
  first query.
- **PormG #1622 — `PormG.config` holds `Configuration.Settings` only.** Code that stored its own
  `PormGSettings` subtype there, or passed its own `config =` dictionary, must use `Settings`.
- **PormG #1672 — `Models.Model_Type` is renamed `Models.ModelType`**, and is public.
- **PormG #1604 — a model holds PormG's own field types only**, and `ModelType.name` is a `String`.
  A field type of your own (`<: PormGField`) raises `ModelDefinitionError`.
- **PormG #1606 — a sysimage or a JuliaC image reads its configuration at run time.** A `load`,
  `load_many` or `register_connection` that runs while the image is built now raises; move it into
  `main`, as the `newapp` boot already does.
- **PormG #1344 — `using PormG` no longer loads `DataFrames` or `CSV`.** Add the one your app uses
  to its own `Project.toml`; a query is a Tables.jl source (`query |> DataFrame`).
- **PormG #1490 — `create`, `get_or_create` and `update_or_create` return the model's fields
  only.** Reading a column the table has and the model does not declare raises `UnknownFieldError`.
- **PormG #1487 — `set_models(models, folder; source = file)` re-binds an edited models file under
  Revise.** Nothing has to change; add `source` to get the reload on a package's run-time bind.

The other entries are refusals at query build (interval and JSON-key arithmetic, `Concat`, `NullIf`,
orderings over uncast JSON keys) and MySQL driver bounds.

### What did not change

**Nitro's public API, the two tables' schemas, and the session and worker stores' behavior.**
Every entry's migration grep was run against `src/ ext/ test/ examples/ docs/ bench/`; none needs
an edit beyond what #791 made.

### How to find the calls to migrate

```bash
# 1. The app's own bound -- this is what blocks resolution.
grep -rn 'PormG = "\^0.9"' --include=Project.toml .

# 2. Models modules bound with `set_models` after a plain `include` (#1602): each needs its
#    `Models.@models` line.
grep -rn 'set_models(' --include=*.jl .

# 3. PormG's own guide, from PormG's OWN environment (it is a weakdep of Nitro, so it is not
#    loadable from the app's project), passing the LOWER BOUND of the bound you are leaving.
julia --project=<pormg-checkout> -e 'using PormG; PormG.upgrade_guide(from = v"0.9.0")'
```

### Migrate your app

```toml
# ✗ before -- will not resolve against this release
PormG = "^0.9"

# ✓ after
PormG = "^0.10"
```

```julia
# ✗ before -- set_models raises ModelDefinitionError on PormG 0.10
module models
import PormG.Models
Product = Models.Model("product", id = Models.IDField(), name = Models.CharField(max_length = 50))
end

# ✓ after -- the line names every model, after their definitions
module models
import PormG.Models
Product::Models.ModelType = Models.Model("product", id = Models.IDField(),
                                         name = Models.CharField(max_length = 50))
Models.@models Product
end
```
