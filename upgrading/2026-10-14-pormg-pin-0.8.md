## PormG moves to `0.8` — an app pinning `^0.7` must move too, and PormG's own guide is yours to run

- **Version**: 0.6.0
- **Nitro ref**: `Project.toml` `[sources]` + `[compat]`; `ext/NitroPormGExt.jl` (`_storable_text`,
  and comments); two tests that drove a PormG internal 0.8 renamed. Nothing an app must change in
  its Nitro code — see *What did not change* below.
- **Recorded**: 2026-10-14
- **Severity**: **breaking (dependency resolution)** — an app carrying its own `PormG = "^0.7"`
  bound does not resolve against this release. The *behavior* changes are PormG's, and this entry
  does not restate them.

### What changed

Both of Nitro's PormG pins moved together, which is the only supported way to move either:

| pin | before | after |
|---|---|---|
| `[sources]` `rev` | `5a5798652508db4f700059bcf2964cfb87697151` (`v0.7.0`'s commit) | `6f558894c68046a948e30bad3018a791a5f9898e` (`v0.8.0`'s commit) |
| `[compat]` | `PormG = "^0.7"` | `PormG = "^0.8"` |

The `rev` is the commit the `v0.8.0` tag points at, not the tag: a tag is mutable and can be
re-pointed, which is exactly the immutability the pin exists to provide. (It is not the annotated
tag *object* either, `94ddc7c…`, which is not a commit.)

That range is **593 commits and 107 upgrade entries** of PormG's 0.8.0 train.

### Who this affects

Every app that reaches PormG directly — which is every app using `NitroPormGExt`, because Nitro
only ever mediates its own two infrastructure tables (`nitro_session`, `nitro_task`). **Nitro does
not insulate you from PormG's 0.8.0 changes**, and this entry is not a summary of them. Run
PormG's guide against your own code.

The train is mostly *refusals*: shapes that ran and returned a wrong or engine-dependent answer
now raise when the query is built. The entries most likely to reach a Nitro app, none of which
Nitro can apply for you:

- **#838 / #831 — the transaction-scope check uses the database a call runs on, and a statement
  runs on the pool it names.** Inside an open transaction, an ORM call routed with
  `.db("<other>")` to a database with no open transaction used to run on the open transaction's
  connection — against *that* transaction's database — and now raises `TransactionError`. A raw
  `fetch(pool_b, …)` inside a block on `pool_a` now runs on `pool_b`, in autocommit, instead of on
  `pool_a`'s transaction connection. The check also looks through enclosing blocks, so a call
  that an enclosing block covers now passes where it was refused.
- **#839 — a task that outlives its `run_in_transaction` / `atomic` block no longer uses the
  block's connection.** Its statements run in autocommit on a connection of their own.
- **#971 / #988 — a value a filter refuses raises `InvalidValueError`, and no refusal prints the
  value.** The 0.7 train (#576) moved read-path refusals to `FilterError`; a value that would be
  bound as a parameter is now `InvalidValueError` again, on reads as on writes. `FilterError`
  remains for arguments that shape the SQL. A handler that catches one type around a `filter()`
  built from request input must be re-checked.
- **#951 / #954 — a string or a `JSONField` value containing a NUL (`'\0'`) raises
  `InvalidValueError`** before any statement is sent. Request input that reaches a filter or a write
  unvalidated can now raise where it used to reach the driver.
- **#876 / #949 — a `Bool` written to or compared with a text field, and an integer other than 0
  or 1 given to a `BooleanField`, raise.**
- **#1033 / #934 — `db_default` refuses a literal value (declare it as `default`) and SQL text
  only one engine can read.** These fail when the models file loads.
- **#1121 / #965 / #800 and siblings — a computed or returned value reads back as the type it
  means.** `Avg` over integers is a `Float64`, a decimal aggregate a `Decimal`, a boolean a `Bool`
  on SQLite too. Code that type-checks or converts a projected value must be re-checked.

### What did not change

**Nothing in Nitro's API or its stores' observable behavior, apart from the U+FFFD substitution
below, and that is the point of confining PormG to `ext/NitroPormGExt.jl`.** Every entry's migration grep was run against `src/ ext/ test/`,
and the hits read one by one: the extension declares only `CharField`, `TextField`, `DateTimeField` and
`FloatField` columns; never uses `Case`, `Round`, `Cast`, `Concat`, joins, aggregates over a
projection or many-to-many managers; binds UTC `DateTime` values rather than `ZonedDateTime`; reads
no value `create()` returns; and parses no error text.

#838 is the one entry that touches the stores' design. Both store models have been bound to their
store's `db_key` since #202, because the old check read the model's binding and ignored `.db()`.
The new check reads the pool `.db(store.db_key)` resolves, so the stores satisfy it on `.db()`
alone; the binding stays. A session or task call inside a transaction opened on a **different**
connection was refused before and is refused now, as `TransactionError` — what the session and
worker docs already promised — unless an enclosing block is open on the store's own connection,
which 0.8 now honors.

#951 reaches two Nitro paths. A session cookie whose id carries a NUL now makes PormG raise on the
lookup; the session store's read path already treats any failed read as "no session" and logs the
exception without the value, so that request is served as anonymous, as an unknown id is. And a
task's error text — its own exception message, which can quote request data — could carry a NUL
into the worker store's `error` column, where PormG would now refuse the terminal write and the
failure record would be lost. The worker store replaces a NUL there with U+FFFD before writing;
before 0.8, PostgreSQL silently cut the text at the NUL and SQLite stored it.

Nitro's public API, the two tables' schemas, and — that substitution aside — the session store's
and worker store's behavior are unchanged.

### How to find the calls to migrate

```bash
# 1. The app's own bound -- this is what blocks resolution.
rg -n '^PormG\s*=' <app>/Project.toml

# 2. The real work. Run PormG's guide from PormG's OWN environment (it is a weakdep of
#    Nitro, so it is not loadable from the app's project), passing the LOWER BOUND of the
#    bound you are leaving -- `v"0.7.0"` for `^0.7`, not the range.
julia --project=<pormg-checkout> -e 'using PormG; PormG.upgrade_guide(from = v"0.7.0")'

# 3. Handlers that catch PormG's error types around a filter built from request input (#971, #988).
rg -n 'FilterError|InvalidValueError' <app>/src

# 4. ORM calls routed to another database while a transaction may be open (#838).
rg -n '\.db\(' <app>/src
```

### Migrate your app

```toml
# ✗ before -- will not resolve against this release
PormG = "^0.7"

# ✓ after
PormG = "^0.8"
```

An app that does not pin PormG itself still inherits Nitro's bound — but it inherits the 0.8.0
*behavior* changes too, so step 2 above is not optional for it either.
