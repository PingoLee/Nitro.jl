## `decode_jwt` — a header `alg` other than `HS256` is now rejected instead of ignored

- **Version**: Unreleased
- **Nitro ref**: [#45](https://github.com/PingoLee/Nitro.jl/issues/45) ; `src/Auth/jwt.jl`
- **Recorded**: 2026-09-21
- **Severity**: **behavior change** — a token that verified before can now fail with
  `AuthError`. Two populations: apps whose issuer stamps a non-`HS256` `alg` while signing with
  the shared HMAC secret (symptom through `BearerAuth`/`CookieAuthMiddleware`: a `401`), and
  apps that read foreign tokens offline with `verify=false` where the issuer stamps a
  non-string `kid` — see *The structural checks are NOT scoped to `verify`* below.

### What changed

`decode_jwt` parsed the header's `alg` and then never read it — HMAC-SHA256 was applied
unconditionally. That is safe, but only by omission, and it meant a token advertising
`alg: "RS256"` whose signature happened to be a valid HS256 MAC was **accepted**. The check is
now explicit.

| header | before | after |
|---|---|---|
| `alg: "HS256"` | verified | verified — unchanged |
| `alg: "RS256"` (valid HS256 MAC) | **accepted** | `AuthError("Unsupported JWT algorithm")` |
| `alg: "none"` | rejected incidentally, on the signature length check | rejected on the algorithm, before any key is resolved |
| no `alg` at all | accepted if the MAC checked out | `AuthError("Unsupported JWT algorithm")` |

The **algorithm** gate sits inside the `verify` branch, so `decode_jwt(...; verify=false)` —
offline inspection, not authentication — still parses a token whatever algorithm its header
claims.

### The structural checks are NOT scoped to `verify` — read this if you inspect tokens offline

Malformed *shape* is rejected on both paths, the same way "a JWT has three segments" always
was. This is a real change to the `verify=false` contract and the reason this entry exists for
more than the `alg` gate:

| input | before, `verify=true` | before, `verify=false` | after, both |
|---|---|---|---|
| non-string header `kid` (`123`, `["a"]`) | `MethodError` on `_resolve_secret` | **no error — claims returned** | `AuthError("Invalid JWT key id")` |
| header segment is not a JSON object (`[]`, a string, a number) | `MethodError` on `get` | `MethodError` on `get` | `AuthError("Invalid JWT header")` |
| claims segment is not a JSON object | `AuthError` (signature) — `MethodError` only for a secret-holder | `MethodError` on `validate_claims` | `AuthError("Invalid JWT claims")` |
| header or claims segment is not decodable base64, or not JSON at all | `ArgumentError` | `ArgumentError` | `AuthError("Invalid JWT encoding")` |
| signature segment is not decodable base64 (e.g. one character) | `ArgumentError` | n/a (not decoded) | `AuthError("Invalid JWT signature encoding")` |
| empty keyset, kid-less token | `BoundsError` from `first(keys(...))` | n/a (no key is resolved) | `AuthError("Unknown JWT key id")` |

Row 3's `verify=true` cell is not a typo: on the verifying path you cannot reach
`validate_claims` without passing the signature check first, so an attacker without the
secret gets `AuthError("Invalid JWT signature")` there. The `MethodError` was reachable
offline, or by someone who could already mint a valid MAC.

The last two rows are length-dependent in a way worth knowing if you are writing your own
fuzz corpus: a **four**-character garbage signature decodes to bytes and always landed on a
clean `AuthError`, while a **one**-character one could not be padded and threw. That is why
a partial fix here reads as complete.

Note the new message is `"Invalid JWT signature encoding"`, distinct from the
`"Invalid JWT signature"` a decodable-but-wrong signature produces. If you match on that
string, match the prefix or add the second case. The distinction is operational: an
undecodable signature is what a **truncated** token looks like — a cookie past the 4KB limit,
a proxy trimming a long header — and that sends you to check transport, not key rotation and
clock skew.

**The guards catch `ArgumentError` only.** `StackOverflowError` from a deeply-nested header
segment, `OutOfMemoryError`, and `InterruptException` all propagate rather than becoming a
`401` — Julia reports a stack overflow as *"program state may be corrupted"*, which is not a
routine authentication failure and should not be reported as one. If you wrap `decode_jwt` in
your own `try`, do the same: catch `AuthError`, not everything.

**Row 1 is the one that can break working code.** Everything else in those rows replaces one
exception with another, and through `BearerAuth`/`CookieAuthMiddleware` every row already
rendered as `401`, because every type in those rows is an `AuthError` and the auth middlewares
map a throwing validator to a 401. (They no longer map *anything* a validator throws — since
[#254](https://github.com/PingoLee/Nitro.jl/issues/254) the three unrecoverable types
propagate. No row above is one of them, so this paragraph is unaffected.) But an
app that reads a foreign token offline — `decode_jwt(t, keyset; verify=false)` to look at
`iss`/`sub` before choosing a validator — and whose issuer stamps a **numeric** `kid` goes
from working to `AuthError`. A numeric `kid` is non-standard but legal JSON and real issuers
emit it.

The check is deliberately not moved inside `verify`: a non-string `kid` is a malformed header
rather than an algorithm choice, and `with_kid=true` promises a `String` it cannot deliver
from `123`.

Note also that the old `MethodError` for a non-string `kid` fired with a plain **string
secret** just as it did with a keyset — `_resolve_secret`'s `kid` parameter is itself typed,
so the failure was never keyset-specific.

`encode_jwt` is unchanged — it has always written `alg: "HS256"`, so tokens Nitro mints are
unaffected. Nitro never loads a public key and never dispatched on `alg`, so the classic
RS256→HS256 confusion attack did not apply before this change either; what the change buys is
that the guarantee is now asserted and regression-tested rather than emergent.

### How to find the calls to migrate

Only a **foreign** issuer can produce an affected token, so look at what mints them, not at
what reads them:

```bash
# 1. Anywhere your app builds a JWT header itself rather than via encode_jwt.
rg -n '"alg"|:alg\b' <app>/src

# 2. Third-party issuers whose tokens you hand to decode_jwt or a jwt_validator.
rg -n 'decode_jwt|jwt_validator' <app>/src

# 3. The offline-inspection path -- the only one where a token that WORKED can now throw.
rg -n 'verify\s*=\s*false' <app>/src
```

For each issuer in (2), decode one real token's header and read its `alg` — no signature needed.
JWT segments are base64**url** and unpadded, so both the alphabet swap and the padding matter
(`"=="` is right only when the length is 2 mod 4, and the commonest header of all —
`{"alg":"HS256","typ":"JWT"}` — is 0 mod 4 and throws):

```julia
using Base64, JSON
function jwt_header(token)
    seg  = replace(String(first(split(token, '.'))), '-' => '+', '_' => '/')
    seg *= repeat("=", mod(4 - mod(length(seg), 4), 4))
    return JSON.parse(String(base64decode(seg)))
end

jwt_header(token)["alg"]           # must be "HS256"
get(jwt_header(token), "kid", nothing)   # must be a String or absent -- see the table above
```

If `alg` is anything else, that issuer's tokens stop authenticating on this release. If `kid`
prints as a number, only your **offline** (`verify=false`) reads change.

### Migrate your app

Nothing to change if every token reaching Nitro is minted by `encode_jwt`, or by any issuer
that correctly labels an HMAC-SHA256 signature.

```julia
# ✗ before -- a hand-built header whose alg was a lie the verifier did not read
header = Dict("alg" => "RS256", "typ" => "JWT")     # signed with an HMAC secret anyway

# ✓ after -- label the algorithm you actually used
header = Dict("alg" => "HS256", "typ" => "JWT")

# ✓ better -- do not hand-build it
token = encode_jwt(claims, secret; expires_in = 900)
```

An issuer that genuinely signs with RS256 was never verifiable by Nitro: it only ever HMACs
with a shared secret. Such a token failed the signature check before and fails the algorithm
check now — the rejection just moved earlier and acquired an accurate message.
