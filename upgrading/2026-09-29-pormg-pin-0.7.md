## PormG moves to `0.7` — an app pinning `^0.6` must move too, and PormG's own guide is yours to run

- **Version**: Unreleased
- **Nitro ref**: `Project.toml` `[sources]` + `[compat]`. No `src/` or `ext/` change was needed —
  see *What did not change* below.
- **Recorded**: 2026-09-29
- **Severity**: **breaking (dependency resolution)** — an app carrying its own `PormG = "^0.6"`
  bound does not resolve against this release. The *behavior* changes are PormG's, and this entry
  does not restate them.

### What changed

Both of Nitro's PormG pins moved together, which is the only supported way to move either:

| pin | before | after |
|---|---|---|
| `[sources]` `rev` | `054b90f6b4de6edacf9a40ebed09c2101e51ee8f` (`v0.6.0`'s commit) | `5a5798652508db4f700059bcf2964cfb87697151` (`v0.7.0`'s commit) |
| `[compat]` | `PormG = "^0.6"` | `PormG = "^0.7"` |

The `rev` is the commit the `v0.7.0` tag points at, not the tag: a tag is mutable and can be
re-pointed, which is exactly the immutability the pin exists to provide. (It is not the annotated
tag *object* either, `c5afa1b…`, which is not a commit.)

That range is **191 commits and 25 upgrade entries** of PormG's 0.7.0 train.

### Who this affects

Every app that reaches PormG directly — which is every app using `NitroPormGExt`, because Nitro
only ever mediates its own two infrastructure tables (`nitro_session`, `nitro_task`). **Nitro does
not insulate you from PormG's 0.7.0 changes**, and this entry is not a summary of them. Run
PormG's guide against your own code.

The entries most likely to reach a Nitro app, none of which Nitro can apply for you:

- **#737 — `migrate()` returns a `MigrationResult`, and nothing pending is no longer an error.**
  "Up to date" used to throw `InvalidMigrationError`, the same type a broken plan raises; a boot
  path that caught it to mean "nothing to do" now receives `:nothing_pending` instead.
  `migrate(…; dry_run_only = true)` is gone too — use `dry_run(…)`.
- **#732 — `Migrations.migrate_to` and `migrate`'s unused `path=` keyword are removed.**
- **#728 — the destructive guard covers every `DROP`, a `TRUNCATE`, and a `DELETE` with no
  `WHERE`.** A hand-edited plan carrying one of those (a `DROP VIEW`, an `ALTER TABLE … DROP x`)
  used to apply without `destructive = true`; it is now refused without it.
- **#576 — every read path raises `FilterError` for a value it cannot coerce.** A handler catching
  `InvalidValueError` around a *read* (a filter built from a query parameter, say) no longer catches
  it. Writes still raise `InvalidValueError`.
- **#765 / #770 — `delete()` and a joined `update()` put their filters on the row they write, and
  on PostgreSQL a cascading delete locks its parents first.** Anything pinning mutation SQL or bound
  values must be re-recorded; a cascade can now deadlock with a writer that locks child then parent,
  and needs UPDATE privilege on each managed table a root filter joins.
- **#648 — SQLite reads a `DecimalField` back as a `Decimals.Decimal`**, as PostgreSQL always did.
- **#253 / #689 — the `pormg-usage` AI skill bundle was restructured.** If you installed it,
  re-run `install_ai_skills()` and delete the stale files.

### What did not change

**No `src/` or `ext/` edit was needed, and that is the point of confining PormG to
`ext/NitroPormGExt.jl`.** Every entry's migration
grep was run against `src/ ext/ test/ docs/` and none required a change: Nitro declares no
`DecimalField`, no foreign keys, no `managed` column, and never calls `migrate`, `bulk_*` or
`Extract`. #765 changes the SQL behind the session store's `delete()` calls — safer, since a waiting
statement now re-checks its own filters — and no Nitro test pinned that SQL. Every `PormG.*` name
the extension binds still exists at the new pin.

The same train moves the worker store's guarded deletes (`try_delete_task!`, the retention sweep)
back onto PormG's `delete()` (#398). That is internal and asks nothing of an app, but it makes
`^0.7` a floor the task fences depend on: #765 is what makes a filter on `delete()` a guard.

Nitro's public API, the session store's and worker store's behavior, and the two tables' schemas
are unchanged.

### How to find the calls to migrate

```bash
# 1. The app's own bound -- this is what blocks resolution.
rg -n '^PormG\s*=' <app>/Project.toml

# 2. The real work. Run PormG's guide from PormG's OWN environment (it is a weakdep of
#    Nitro, so it is not loadable from the app's project), passing the LOWER BOUND of the
#    bound you are leaving -- `v"0.6.0"` for `^0.6`, not the range.
julia --project=<pormg-checkout> -e 'using PormG; PormG.upgrade_guide(from = v"0.6.0")'

# 3. Boot paths that read migrate()'s result or caught its "nothing pending" error (#737).
rg -n -A6 'migrate\(' <app>/src | rg 'MigrationError|isnothing|=== nothing|dry_run_only'

# 4. Read-path handlers that catch the old error type (#576).
rg -n 'InvalidValueError' <app>/src | rg -v 'insert|update|bulk|create|save'
```

### Migrate your app

```toml
# ✗ before -- will not resolve against this release
PormG = "^0.6"

# ✓ after
PormG = "^0.7"
```

An app that does not pin PormG itself still inherits Nitro's bound — but it inherits the 0.7.0
*behavior* changes too, so step 2 above is not optional for it either.
