## PormG moves to `0.9` — an app pinning `^0.8` must move too, name its environment at every `load`, and bind its models in `main()`

- **Version**: Unreleased
- **Nitro ref**: #790 ; `Project.toml` `[sources]` + `[compat]`; `ext/NitroPormGExt.jl` (the
  `newapp` boot, the environment bridge's comments); `src/newapp.jl`, `src/exts.jl`,
  `src/environment.jl` (docstrings); `docs/src/tutorial/bigger_applications.md`,
  `docs/src/tutorial/environment.md`
- **Recorded**: 2026-10-29
- **Severity**: **breaking (dependency resolution, and the boot)** — an app carrying its own
  `PormG = "^0.8"` bound does not resolve against this release, and two PormG 0.9 refusals reach
  the boot Nitro documented: a `load` with no environment, and `@import_models` in a package's
  module body. Nitro's own API is unchanged.

### What changed

Both of Nitro's PormG pins moved together. **Only 0.9 is supported**: the bound is `^0.9`, not
`0.8, 0.9`.

| pin | before | after |
|---|---|---|
| `[sources]` `rev` | `6f558894c68046a948e30bad3018a791a5f9898e` (`v0.8.0`'s commit) | `5531c68cf482ca0723878bc6c593720a8cbf3502` (`v0.9.0`'s commit) |
| `[compat]` | `PormG = "^0.8"` | `PormG = "^0.9"` |

As before, the `rev` is the commit the tag points at, not the tag, which can move.

**The boot `Nitro.newapp` writes changed**, because two of PormG 0.9's entries refuse what it did:

- **PormG #1228 / #1256 — outside an interactive session, `Configuration.load`, `load_many` and
  `register_connection` need `env=` or `PORMG_ENV`.** They used to fall back to the file's
  `default_env:`, then `"dev"`. A service, a script, a test run and a precompile worker are all
  outside an interactive session. Nitro's bridge publishes `NITRO_ENV` into `PORMG_ENV` only when
  `NITRO_ENV` is set, so a generated app run as `julia app.jl`, or from a unit file, with neither
  variable set raised `InvalidConfigurationError` at boot. The boot now passes
  `env = something(sync_pormg_env!(), current_env())`: a `PORMG_ENV` the deployment set, as
  before; else `NITRO_ENV` (or `GENIE_ENV`), which the bridge publishes and returns, as before;
  else `current_env()`'s `"dev"`, the environment the startup banner reports. Only the last step
  changed: `"dev"` replaces the file's `default_env:`, which is no longer read. Write
  `something(sync_pormg_env!(), …)`, not a bare `env = current_env()`: an explicit `env=` outranks
  `PORMG_ENV`, so the bare form would move a box that exports `PORMG_ENV=prod` with no `NITRO_ENV`
  onto `dev`.
- **PormG #1226 — `@import_models` refuses a models folder that no `load` has loaded, outside a
  REPL.** It used to load the folder implicitly. The tutorial put `@import_models` in the module
  body and `load_many` in `main()`, and a package's module body runs only in the precompile
  worker, so that app **does not precompile** on 0.9. The models are now `include`d in the module
  body, which defines them and reads nothing, and `main()` binds them after loading:
  `PormG.Models.set_models(models, joinpath(pkgdir(@__MODULE__), "db"))`. PormG's own fix, a
  `load` in the module body and again in `__init__`, was not taken: the module-body `load` reads
  `db/connection.yml`, password included, while the package precompiles, and a JuliaC image keeps
  every global, PormG's configuration among them.

### Who this affects

Every app that uses `NitroPormGExt`, which is every app that reaches PormG directly: Nitro
mediates only its own two tables (`nitro_session`, `nitro_task`), and **does not insulate an app
from PormG's 0.9.0 changes**. This entry is not a summary of them; run PormG's guide against
your own code. Beyond the two above, the entries most likely to reach a Nitro app:

- **PormG #1237 — `select_for_update()` must run inside a transaction on SQLite too.** It ran
  silently under autocommit there, and raised only on PostgreSQL.
- **PormG #1232 — a `load` whose adapter's driver package is not loaded fails at the `load`**,
  not at the first query. An app written by `Nitro.newapp` with the setup prompt abandoned has no
  driver: it now fails in `main()`, at `load_many`, naming the package to add.
- **PormG #1225 — a second `load` of a folder already loaded with the same environment is a
  no-op.** A boot that reloads to pick up an edited `connection.yml` needs `force = true`.
- **PormG #1231 — a models file that still ends with `Models.set_models(@__MODULE__, @__DIR__)`**
  now refuses an unloaded folder from inside its own `include`. Delete the line; with the boot
  below, `main()` does the binding.
- The rest of the 67 entries are refusals on query expressions (`Case`, `Cast`, date and
  interval arithmetic, joined `update`s, row locks beside outer joins) that ran and returned an
  engine-dependent answer, and now raise when the query is built.

### What did not change

**Nitro's public API, the two tables' schemas, and the session and worker stores' behavior.**
Every entry's migration grep was run against `src/ ext/ test/ bench/`. The extension declares
only `CharField`, `TextField`, `DateTimeField`, `FloatField`, `IntegerField` and `BooleanField`
columns, uses no `Case`, `Cast`, join, aggregate or many-to-many manager, binds its models with
neither `set_models` nor `@import_models`, and runs its one `select_for_update` (the external
queue's claim) inside `run_in_transaction` already. `sync_pormg_env!` behaves as before: it
publishes `NITRO_ENV` when it is set and nothing when it is not, so a `load` with no `env=` still
gets `NITRO_ENV` when one is set.

### How to find the calls to migrate

```bash
# 1. The app's own bound -- this is what blocks resolution.
rg -n '^PormG\s*=' <app>/Project.toml

# 2. Loads and connections with no environment (#1228, #1256) -- in src/, and in the test suite
#    and scripts, which are not interactive either. Each needs
#    `env = something(sync_pormg_env!(), current_env())` (a test suite: `env = "test"`), unless
#    every process that runs it exports NITRO_ENV or PORMG_ENV.
rg -n --type julia 'Configuration\.load(_many)?\(|register_connection\(' <app> | rg -v 'env *='

# 3. Models registered in a module body (#1226), and the legacy registration line (#1231).
rg -n '@import_models|@models_module|set_models\(' <app>/src <app>/db

# 4. PormG's own guide, from PormG's OWN environment (it is a weakdep of Nitro, so it is not
#    loadable from the app's project), passing the LOWER BOUND of the bound you are leaving.
julia --project=<pormg-checkout> -e 'using PormG; PormG.upgrade_guide(from = v"0.8.0")'
```

### Migrate your app

```toml
# ✗ before -- will not resolve against this release
PormG = "^0.8"

# ✓ after
PormG = "^0.9"
```

```julia
# ✗ before -- does not precompile on PormG 0.9, and refuses at boot with NITRO_ENV unset
module MyApp
using Nitro, PormG, SQLite
const app = App(mod = @__MODULE__)
PormG.@import_models "../db/models.jl" models
const appM = models
# ...
function main(; kwargs...)
    sync_pormg_env!()
    PormG.Configuration.load_many(["db"]; root = pkgdir(@__MODULE__))
    # ...
end
end

# ✓ after -- the module body only defines; main() loads in a named environment, then binds
module MyApp
using Nitro, PormG, SQLite
const app = App(mod = @__MODULE__)
include("../db/models.jl")
const appM = models
# ...
function main(; kwargs...)
    env = something(sync_pormg_env!(), current_env())   # PORMG_ENV, else NITRO_ENV, else "dev"
    PormG.Configuration.load_many(["db"]; root = pkgdir(@__MODULE__), env)
    PormG.Models.set_models(models, joinpath(pkgdir(@__MODULE__), "db"))
    # ...
end
end
```

`connection.yml` needs a block for every environment the app runs in: `NITRO_ENV=prod` reads
`prod:`, and with neither `NITRO_ENV` nor `PORMG_ENV` set the app reads `dev:`, whatever
`default_env:` says. A SQLite `PormG.setup` writes only `dev:`. A box that relied on
`default_env: prod` with no variable exported must now export `NITRO_ENV=prod`:

```bash
# Units, images and compose files that launch the app: each should set NITRO_ENV or PORMG_ENV.
rg -n 'NITRO_ENV|PORMG_ENV|GENIE_ENV' <deploy-files>
rg -n '^default_env:' <app>/db/connection.yml
```
