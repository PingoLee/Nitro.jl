## PormG moves to `0.6` — an app pinning `^0.5` must move too, and PormG's own guide is yours to run

- **Version**: 0.4.0
- **Nitro ref**: `Project.toml` `[sources]` + `[compat]`. No `src/` or `ext/` change — see
  *What did not change* below.
- **Recorded**: 2026-09-21
- **Severity**: **breaking (dependency resolution)** — an app carrying its own `PormG = "^0.5"`
  bound does not resolve against this release. The *behavior* changes are PormG's, and this entry
  does not restate them.

### What changed

Both of Nitro's PormG pins moved together, which is the only supported way to move either:

| pin | before | after |
|---|---|---|
| `[sources]` `rev` | `6d708b4d4b9a1bdefca89fe44c29652574c931c0` (`0.5.0`, post-`v0.5.0`) | `054b90f6b4de6edacf9a40ebed09c2101e51ee8f` (the `v0.6.0` tag) |
| `[compat]` | `PormG = "^0.5"` | `PormG = "^0.6"` |

The `rev` is the commit the `v0.6.0` tag points at, not the tag: a tag is mutable and can be
re-pointed, which is exactly the immutability the pin exists to provide. It is deliberately **not**
`main`, which at the time of writing carried 13 further commits and an unreleased upgrade entry.

That range is **168 commits and 22 upgrade entries** of PormG's 0.6.0 train.

### Who this affects

Every app that reaches PormG directly — which is every app using `NitroPormGExt`, because Nitro
only ever mediates its own two infrastructure tables (`nitro_session`, `nitro_task`). **Nitro does
not insulate you from PormG's 0.6.0 changes**, and this entry is not a summary of them. Run
PormG's guide against your own code.

The entries most likely to reach a Nitro app, none of which Nitro can apply for you:

- **#527 — a one-time SQLite *data* repair.** Rows written by `update("<a DateTimeField>" => F(...)
  ± <duration>)` under the old renderer hold a non-canonical timestamp string that no longer matches
  any filter. PormG's entry carries the exact `UPDATE ... strftime(...)` statement and explains why
  all three of its `WHERE` clauses are load-bearing. Nitro's own stores never wrote such a row, so
  `nitro_session` and `nitro_task` need nothing; your tables may.
- **#545 — `database: ":memory:"` is now a SQLite keyword, not a relative path**, and pairing it
  with `sqlite_split_read_write` is refused at construction. On POSIX this was silently an on-disk
  file *named* `:memory:`; data written there no longer survives, and a pool no longer shares it.
- **#550 — one models folder now resolves to exactly one connection key.** `Configuration.load`
  returns the key it registered, which may not be the string you passed, and a folder registered
  under an implicit absolute-path key is migrated and the old entry deleted.
- **#564 — temporal columns read back as Julia values on SQLite.** Code that compensated by parsing
  the string itself now receives a typed value.
- **#544 — table columns are created in declaration order.** Only visible if you pin generated DDL
  as a string; re-record that golden once.

### What did not change

**No `src/` or `ext/` edit was needed, and that is the point of confining PormG to
`ext/NitroPormGExt.jl`.** Every entry's migration grep was run against `src/ ext/ test/ docs/src/`
and all but one came back empty; all 29 PormG symbols the extension binds still exist at the new
pin. The one hit was #564 on `_parse_db_datetime` (`ext/NitroPormGExt.jl:242`), which already
accepts `DateTime`, any `Dates.AbstractDateTime` (the `ZonedDateTime` PormG now hands back on
SQLite as well as PostgreSQL) **and** the raw string shapes — the "tolerate both pins" form PormG's
own entry recommends. `test/extensions/pormg_session_tests.jl:559` pins all of them.

Nitro's public API, the session store's and worker store's behavior, and the two tables' schemas
are unchanged.

### How to find the calls to migrate

```bash
# 1. The app's own bound -- this is what blocks resolution.
rg -n '^PormG\s*=' <app>/Project.toml

# 2. The real work. Run PormG's guide from PormG's OWN environment (it is a weakdep of
#    Nitro, so it is not loadable from the app's project), passing the LOWER BOUND of the
#    bound you are leaving -- `v"0.5.0"` for `^0.5`, not the range.
julia --project=<pormg-checkout> -e 'using PormG; PormG.upgrade_guide(from = v"0.5.0")'

# 3. Apps on SQLite that ever ran date arithmetic through `update` need #527's data repair.
rg -n 'update\(.*F\(.*[+-].*(Day|Week|Month|Year|Hour|Minute|Second|Interval)' <app>/src

# 4. Anything that re-parsed a temporal column PormG handed back as text (#564).
rg -nE '(Date|DateTime|Time)\(row\[|parse\(.*row\[' <app>/src
```

### Migrate your app

```toml
# ✗ before -- will not resolve against this release
PormG = "^0.5"

# ✓ after
PormG = "^0.6"
```

An app that does not pin PormG itself still inherits Nitro's bound — but it inherits the 0.6.0
*behavior* changes too, so step 2 above is not optional for it either.
