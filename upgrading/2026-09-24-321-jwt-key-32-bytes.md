## A JWT secret must be at least 32 bytes (#321)

- **Version**: Unreleased
- **Nitro ref**: [#321](https://github.com/PingoLee/Nitro.jl/issues/321) ; `src/Auth/keyset.jl`
- **Recorded**: 2026-09-24
- **Severity**: **breaking (auth).** An app whose JWT key is shorter than 32 bytes now fails at
  startup. Its tokens were open to offline brute force.

### What changed

The only JWT secret Nitro used to refuse was an empty one, or one made only of NUL bytes.
`jwt_validator("secret")` worked. So did a one-character `JWTKeyset` key. RFC 7518 §3.2 requires
an HS256 key of at least 256 bits, and a single token issued under a short key lets anyone test
guesses against it offline.

Every place a JWT key enters now refuses a key shorter than **32 bytes** with an `ArgumentError`
that states the length and never the key:

| Call | When it throws |
|---|---|
| `jwt_validator(secret)`, `jwt_validator(keyset)`, `jwt_validator(dict)` | at construction, which is app startup |
| `JWTKeyset(...)`, including a lifted `Dict` | at construction. Verify-only keys are checked too |
| `encode_jwt(claims, secret)` | on the call |
| `decode_jwt(token, secret)` | on the call, whenever it verifies a signature |

`decode_jwt(...; verify = false)` never reads the key, so it is unaffected.

The length is counted in **bytes**, the way HMAC sees the key. An empty key, and a run of NULs,
still gets the more specific "empty HMAC key" message, whatever its length. This is the same
floor that `configcookies` has applied to cookie secrets since #309.

### How to find the calls to migrate

The error message names the problem:

```text
ArgumentError: the JWT secret is 6 bytes; an HS256 key must be at least 32 random bytes (RFC 7518 §3.2)…
ArgumentError: JWTKeyset: the secret for kid "partner" is 12 bytes; an HS256 key must be…
```

Before deploying, find every place a JWT key enters, and check the length of the value each one
receives. The environment variable is the usual place to check:

```bash
grep -rnE 'jwt_validator\(|encode_jwt\(|decode_jwt\(|JWTKeyset\(' --include=*.jl .
```

Tests that sign tokens with a literal such as `"secret"` or `"test-key"` fail in the same way.

### Migrate your app

Generate a key once and put it in the environment of every service that signs or verifies:

```sh
julia -e 'using Nitro; println(bytes2hex(Nitro.Crypto.secure_random_bytes(32)))'
```

```julia
# ✗ before — 6 bytes, guessable from any one token
validator = jwt_validator("secret")

# ✓ after — 32+ random bytes, read from the environment
jwt_secret = get(ENV, "JWT_SECRET", nothing)
isnothing(jwt_secret) && error("JWT_SECRET must be set")
validator = jwt_validator(jwt_secret)
```

```julia
# ✗ before — a short partner key in a registry
JWTKeyset("self" => ENV["JWT_SELF"]; verify = ["partner" => "partner-key"])

# ✓ after — every key 32+ bytes, verify-only ones included
JWTKeyset("self" => ENV["JWT_SELF"]; verify = ["partner" => ENV["JWT_PARTNER"]])
```

A new key invalidates every token signed with the old one. To rotate without logging everyone out,
sign with the new key and keep the old key as a verify-only key until its tokens have expired.
That only works while the old key is still accepted, so on this release it has to be 32 bytes or
more as well. If it is shorter, the one-time logout cannot be avoided. Tokens that other services
issue under a shared short key must be re-issued too, once those services have the new key.

For tests, pad a readable label to the minimum, e.g. `rpad("test-key", 32, '.')`.
